# 业务编号与审计规范

> 适用于 WMS 项目当前阶段的统一约定。本文档优先约束业务编号的生成、存储与展示方式，以及审计日志的基本写入边界。

## 1. 基本原则

1. 数据库主键 `id` 只用于内部关联，不加业务前缀。
2. 业务单号 `order_no`、`movement_no` 这类对人可见、会搜索、会打印的编号，可以带固定前缀。
3. 前缀一旦作为业务编号规则的一部分，应当在后端生成后直接写入数据库，不要只在 UI 层临时拼接。
4. UI 层只负责展示，不负责决定编号规则。
5. Repository 层只负责持久化，不负责重新加工业务编号。

## 2. 编号与前缀的区分

### 2.1 需要加前缀的字段

以下字段建议带前缀：

- 入库单号 `order_no`
- 出库单号 `order_no`
- 调拨单号 `order_no`
- 库存流水号 `movement_no`
- 其他面向业务人员查看的单据编号

示例：

- `INB-20260807-0001`
- `OUT-20260807-0001`
- `TRF-20260807-0001`
- `MOV-20260807-0001`

### 2.2 不需要加前缀的字段

以下字段不建议带前缀：

- 数据库主键 `id`
- 外键 `order_id`
- `product_id`
- `warehouse_id`
- `operator_id`
- 其他纯数据库关联字段

这些字段应保持纯数字，便于索引、关联和调试。

## 3. 存储规则

### 3.1 业务单号的存储位置

如果某个编号定义为业务编号的一部分，那么应当：

- 编号格式规则应由应用层统一约束
- 具体编号生成可以由 Repository 或基础设施层完成
- 如果编号生成依赖数据库序号、唯一键、锁或事务上下文，应在 Repository/基础设施层生成并与主业务写入保持同一事务边界
- Repository 将生成后的完整业务编号写入数据库
- UI 原样展示

不要采用“数据库里存纯数字，UI 再临时加前缀”的方式，除非这个编号只用于界面展示。

### 3.2 数据库示例

- `inbound_orders.order_no`：存储完整单号，例如 `INB-20260807-0001`
- `stock_movements.movement_no`：存储完整流水号，例如 `MOV-20260807-0001`
- `audit_logs.target_id`：通常存数据库主键，不强制加前缀

## 4. 各层职责

### 4.1 Service / Application

- 约束业务编号的格式要求
- 提供业务动作上下文，例如当前用户、操作类型、操作来源
- 组装审计日志需要的业务语义
- 不拼接 SQL，不直接访问编号表或库存表

### 4.2 Repository / Infrastructure

- 可以在需要数据库序号、唯一键、锁或事务上下文时生成业务编号
- 将完整业务编号写入数据库
- 读取数据库并原样返回
- 不由 UI 临时补前缀
- 通过数据库唯一约束兜底保证编号不重复

### 4.3 UI

- 显示业务编号
- 提供搜索、筛选、复制
- 不决定编号格式，不负责补前缀

## 5. 审计日志规范

### 5.1 审计日志的定位

审计日志属于横切能力，用于记录“谁在什么时间对什么对象做了什么操作”。

它不是一个独立的核心业务流程，但它必须参与到关键事务中，例如：

- 创建产品
- 修改产品
- 确认入库单
- 确认出库单
- 其他会修改核心数据的操作

### 5.2 审计日志写入原则

1. 审计日志应和主业务写入放在同一个事务里。
2. 主业务成功，审计日志也应成功。
3. 任何一步失败，都应整体回滚。
4. 审计日志内容应尽量描述业务动作本身，而不是依赖后续查询再拼接。

### 5.3 审计日志内容建议

建议保留这些信息：

- `operator_id`
- `username`
- `action`
- `target_type`
- `target_id`
- `detail`
- `created_at`

其中 `detail` 建议存结构化内容，例如 JSON。

示例：

```json
{
  "module": "inbound",
  "action": "confirm",
  "orderId": 123,
  "orderNo": "INB-20260807-0001",
  "fromStatus": "draft",
  "toStatus": "confirmed",
  "warehouseId": 3,
  "operatorId": 7
}
```

## 6. 对当前项目的建议

1. 入库单号建议使用前缀，例如 `INB-YYYYMMDD-序号`。
2. 库存流水号建议使用独立前缀，例如 `MOV-YYYYMMDD-序号`。
3. `audit_logs.target_id` 保持内部 ID 即可，不强制加前缀。
4. 审计写入应先做轻量公共模块，再接入各个会改数据的 repository 或事务流程。
5. `ProductEditDialog`、单位、分类等基础引用数据应通过只读 service 提供，不要在 UI 中硬编码。

## 7. 推荐落地顺序

1. 先统一业务编号的格式约定。
2. 具体编号生成先放在当前 Repository 或基础设施实现中，不急于抽独立编号规则模块。
3. 再补轻量审计写入能力。
4. 再把审计接入入库确认、产品新增/修改等关键流程。
5. 最后再补单位、分类等 lookup service。

## 8. 一句话约定

**对人可见、可搜索、可打印的编号加前缀；对数据库内部关联字段不加前缀。编号格式由后端统一约束，具体生成可由 Repository/基础设施层在事务中完成，UI 只负责展示。**
