# WMS 计划对齐与动态重排

## 权威信息顺序

安排任务前按以下顺序核对：

1. 原始详细计划：`D:\笔记\仓库管理系统\C++_Qt_MySQL_仓库管理系统_优化版详细实施计划.md`。
2. 当前仓库中的源代码、CMake、测试和实际构建结果。
3. `docs/daily-plan.md` 中记录的滚动进度。
4. 当前对话中用户明确确认的完成情况和新约束。

如果原始详细计划不可访问、章节缺失或相互矛盾，明确指出问题并询问用户，不得自行补全日程。

## 每次规划的工作流

1. 读取 `docs/daily-plan.md`，确认已完成模块、暂缓项和当前候选任务。
2. 检查相关代码、CMake 和测试，不能只根据聊天记录判断完成状态。
3. 在详细计划中定位当前周级阶段、目标、重点、交付和验收标准。
4. 分析模块依赖，选择能推进当前阶段交付的下一项关键任务。
5. 维护“当前任务加后续 2 至 3 天”的滚动计划。
6. 每天列出目标、知识点、实施任务、测试任务和验收标准。
7. 用户确认构建和测试通过后，才把对应任务标记为完成。

## 允许的动态调整

- 可以根据依赖关系拆分、合并或重新排序同一阶段及相邻阶段的任务。
- 可以保留已经提前完成的模块，不要求为了匹配日期重复实现。
- 可以把非阻塞增强项标记为“暂缓”，优先完成当前纵向切片。
- 调整顺序时要说明原计划位置、当前实际状态和调整理由。

## 禁止的偏离

- 不得因为某项技术在计划中被提及，就直接把它安排为当前日程。
- 不得把学习资源、后期增强项或总体功能清单误判为某一天的任务。
- 不得跳过当前阶段的必要依赖，直接进入后期 UI、报表、看板或性能优化。
- 不得把 Codex 自己建议的功能表述成原计划的明确要求。
- 未找到可靠依据时，不得声称“计划中确定存在”。

## 模块选择原则

优先级从高到低：

1. 当前阶段交付的必要依赖。
2. 能形成可运行、可测试纵向切片的任务。
3. 已有代码的闭环工作，例如补齐验证、测试和接入。
4. 计划中的普通任务。
5. 可选增强和非阻塞优化。

## 每日讲解要求

- 使用中文，面向软件开发新手，但保持工程术语准确。
- 先解释模块在整体架构中的位置，再讲接口和实现。
- 解释为什么这样设计、替代方案有什么代价、常见错误是什么。
- 默认指导用户自己实现；除非用户明确要求，否则不直接代写整个模块。
- 创建任何新文件前必须询问用户。

## 计划更新格式

`docs/daily-plan.md` 应保留：

- 当前完成进度。
- 明确的暂缓任务。
- 当前任务及后续 2 至 3 天。
- 每天的目标、知识点、实施任务和验收标准。

发现旧计划存在错误时，先核对详细计划和代码，再修正并说明原因。
